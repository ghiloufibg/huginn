# M15.1 — Last deployment date and time in the services preview  (status: implemented, pending real-cluster check V-2)

**Goal:** when a microservice is selected on the services screen, its preview panel shows **when it was last deployed**, date and hour, so the question "did this start after the deploy?" is answered without leaving Huginn or running `kubectl rollout history`. One line per workload of the repository (a microservice can have several).

Implemented with the owner's recommendations (see [D-072](../DECISIONS.md)): completion time, a DEPLOYED section, no pipeline-annotation source, the `pods since` wording, `AGE` unchanged. Where the code differs from the text below, the code and D-072 win: `LastDeployment(w, pods)` takes no `ContainerFilter` (nothing in it needs one); there is no `DeployAnnotation` source or `Stamped` field (§6 was left out of the first cut); the DEPLOYED section is given room **before** the pod list, not after the workloads (a four-workload service otherwise showed `+4 more` instead of its dates); and the demo pods now carry a `Revision`. Facts below come from the code (cited) and from the Kubernetes documentation (cited); anything that is an assumption is marked **to verify** and is added to the real-GKE QA plan (§9).

## 1. What exists today, and what is missing

| Fact | Where | Consequence |
|---|---|---|
| The preview has four sections: WORKLOADS, PODS, WARNINGS, SIDECARS; WORKLOADS shows `Kind name  r/d ready  u/d updated  <image tag>` | `tui/preview.go` `workloads()` | No time is shown for the rollout. |
| The `AGE` column of the services table is `ServiceSummary.Created`, the **oldest workload object's creation time**, not a deployment time | `domain/status.go:86`, `tui/services.go:363` | It can say "42d" for a service deployed 5 minutes ago. It must not be reused for this, and the new line should not be mistaken for it. |
| Pods carry `Created`, `Started` and `Revision` (the pod-template hash of Deployments, the controller-revision hash of StatefulSets/DaemonSets) | `kubernetes/convert.go` `toPod`, `revision()` | A rollout can be dated from the pods already watched, with no new request. |
| `Workload` carries `Created`, `Annotations`, replica counts and `Progressing`, but **no rollout time**; `fromDeployment` ignores `status.conditions` | `kubernetes/convert.go` | The controller's own record of the rollout is read from objects already in the informer, just not converted. |
| The adapter deliberately avoids ReplicaSets and Jobs: `ownerOf` derives the owner from names so **no permission on them is needed** | `convert.go:101` | A solution that watches ReplicaSets would widen the permissions Huginn asks for. Rejected below. |
| `ServiceSummary.WorkloadStates []Workload` already flows from the catalog to the preview | `domain/service.go:52` | A new `Workload` field reaches the preview with no change to the catalog. |
| `domain.WorkloadVersion` already groups a workload's pods by revision and image tag to say `old→new` or `tag (restart)` | `domain/status.go:159` | The pod-based date uses the same grouping; one place to read for both. |

## 2. What "last deployment" means here

A deployment is a **change of the pod template that the cluster has rolled out**: a new image, a changed environment variable, `kubectl rollout restart`, or a rollback. It is **not** a change of replica count, a pod restart after a crash, or a pod moved by a node upgrade. The time shown is **when that rollout completed**; while one is running the line says so and shows when it started.

Why completion and not start: the question the user is asking is usually "since when does the running code behave like this", and the new code serves traffic once its pods are ready. The start of a rollout is still shown while it is in progress.

## 3. Sources, in order of preference

All three use only objects Huginn already watches (Deployments, StatefulSets, DaemonSets, CronJobs, pods): **no new permission, no new informer, no new request.**

| # | Source | Used for | Strength | Weakness |
|---|---|---|---|---|
| 1 | **Controller record**: `Deployment.status.conditions[type=Progressing]` with `status=True`, `reason=NewReplicaSetAvailable`; its `lastUpdateTime` | Deployments, rollout complete | Survives pod replacement, scale changes and node upgrades; a rollback or restart creates a new rollout and so moves it | `lastUpdateTime` is documented only as "last time this condition updated"; that it stays fixed once the rollout is complete is **to verify** on a real cluster (V-2 below) |
| 2 | **Pods**: among the workload's pods (not deleted), group by `Revision`; the newest revision is the group whose earliest `Created` is latest; the date is that group's earliest `Created` | StatefulSets, DaemonSets, a Deployment with no usable condition, bare pods | Needs nothing; right after a rollback (new pods are created for the old template) | If every pod of the current revision was later replaced (node upgrade, eviction), the date moves to the replacement: it is a **lower bound on the age**. GKE auto-upgrades make this realistic |
| 3 | **Annotation** written by the user's pipeline, named in the config folder (§6) | Optional, any kind | The only source that knows the real pipeline's time | Needs the pipeline to write it |

CronJobs have no pods that stay and no rollout; they show `no rollout record` (dim). A CronJob's schedule is not a deployment.

Rejected sources, with the reason:

| Rejected | Why |
|---|---|
| Newest **ReplicaSet** `creationTimestamp` | Wrong after `kubectl rollout undo`: the controller **reuses** the old ReplicaSet, so its creation time stays the old one (documented: the `deployment.kubernetes.io/revision-history` annotation exists for this reuse). Also needs list/watch on ReplicaSets, up to 10 per Deployment by default, and widens the permissions |
| `ControllerRevision` of a StatefulSet | New permission and informer for a value pods already give |
| `metadata.managedFields[].time` | Documented as updated "when a manager changes any owned field value", which includes `spec.replicas` changes by an autoscaler: it would move on scaling, not only on deploys |
| `Condition.lastTransitionTime` | Only changes when the status changes, and `Progressing` stays `True` across rollouts: it would stay at the first rollout ever |
| `kubectl.kubernetes.io/last-applied-configuration` | Holds no time, and is absent when the object is not managed by `kubectl apply` |
| Image-registry push time | Not known to the cluster; belongs to a registry adapter, out of scope |

## 4. Design

### 4.1 Domain (`internal/core/domain`, stdlib only)

```go
// Workload gains one field:
//   RolloutDone time.Time // when the controller last completed a rollout of
//                         // the pod template; zero when the kind keeps no such record
//   Stamped     time.Time // value of the configured annotation (§6); zero when none

type DeployInfo struct {
    At         time.Time    // when the current version was deployed
    Source     DeploySource // DeployController | DeployPods | DeployAnnotation | DeployUnknown
    InProgress bool         // a rollout is running: At is then when it started
    Updated, Desired int    // replicas on the new template, for the in-progress line
}

// LastDeployment is pure: it reads the workload as watched and its pods.
func LastDeployment(w Workload, pods []Pod, f ContainerFilter) DeployInfo
```

Rules, in order:
1. `Stamped` set → `DeployAnnotation` at `Stamped`.
2. `w.Progressing` → `InProgress`, `At` = earliest `Created` of the newest revision's pods (the rollout's first new pod); source `pods`. If there are no new pods yet, `At` is zero and the line says "rollout starting".
3. `RolloutDone` set → `DeployController` at `RolloutDone`.
4. Pods exist → `DeployPods` at the newest revision's earliest `Created`.
5. Otherwise `DeployUnknown`.

Pure function, table-tested; no clock inside (the caller formats the age).

### 4.2 Adapter (`adapters/driven/kubernetes/convert.go`)

`fromDeployment` reads the condition and sets `RolloutDone` only when `status=True` and `reason=NewReplicaSetAvailable` (the documented complete state). Other kinds leave it zero. `workload()` copies the configured annotation (§6) into `Stamped` by name, parsing RFC 3339; an unparsable value is ignored (never an error on screen). The adapter keeps translating library types to domain types: no `appsv1.DeploymentCondition` leaves it.

### 4.3 Demo (`adapters/driven/demo`)

The generated Deployments get a `RolloutDone` consistent with their pods (a recent rollout for the rolling-out service, days ago for the others, one with none) so `--demo` and the golden tests exercise every state deterministically.

### 4.4 TUI (`adapters/driving/tui/preview.go`)

A new section **DEPLOYED**, one line per workload, between WORKLOADS and PODS:

```
WORKLOADS  Deployment payment-service  2/2 ready  2/2 updated  v2.14.3
DEPLOYED   payment-service  Nov 1 14:32  3h ago
PODS       …
```

| State | Line (dim = secondary) |
|---|---|
| Controller record | `payment-service  Nov 1 14:32  3h ago` |
| Pods only | `payment-service  pods since Nov 1 14:32  3h ago` (the wording tells the user it is the pods' age, so it needs no legend) |
| Annotation | `payment-service  Nov 1 14:32  3h ago  (annotation)` |
| In progress | `payment-service  rolling out since Nov 1 14:30  4m ago  1/2 updated` in the warning style |
| Starting | `payment-service  rolling out, no new pod yet` |
| None / CronJob | `payment-service  no rollout record` (dim) |

- The date is in the machine's time zone (`Model.location()`, introduced by M15): `Jan 2 15:04`; with the year when it is not the current one; the age uses the existing `shortAge`, and a negative age (clock skew between the API server and this machine) shows `just now`, never a negative.
- **Why a section and not the WORKLOADS line:** that line is already about 70 columns; appending 28 more clips it below about 100 columns, and the side panel is only 40% of the screen. A section reuses the existing allocation (one line per section first, the rest as space allows, `+n more`).
- A microservice with several workloads shows several lines, ordered like WORKLOADS.
- Hidden when the panel has no room, like the other sections; `p` and the layout rules are unchanged.

### 4.5 What does not change

Ports, the catalog, the services table (including `AGE`), the logs and Kafka screens, the config schemas (unless §6 is accepted), `archtest` (no new package).

## 5. Edge cases (each is a unit test, and the first six also a real-cluster case)

| Case | Expected |
|---|---|
| New image | Moves to completion time; during the rollout, "rolling out since" |
| `kubectl rollout undo` | Moves (a new rollout of the old template) |
| `kubectl rollout restart` | Moves (template annotation changes) |
| Scale up/down, HPA, `kubectl delete pod`, crash restarts | Does **not** move (source 1); source 2 moves only if every pod of the revision was replaced |
| Node upgrade or eviction of all pods | Source 1 unchanged; source 2 moves: the reason source 1 is preferred |
| Rollout stuck (`ProgressDeadlineExceeded`, bad image) | `rolling out since`, with the updated count; the previous completion time is not shown as current |
| Scaled to zero | Source 1 still dated; pods-only says `no rollout record` |
| StatefulSet with a partition, DaemonSet | Pods source; a partitioned StatefulSet keeps `rolling out` (as `Progressing` does today) |
| Bare pod, standalone workload | Its own `Created` |
| Two workloads, one repository | Two lines |
| Time zone, DST, year change, clock skew | Local zone shown; no negative age |

## 6. Optional: a deployment time written by the pipeline

Companies often stamp their own deploy time (an annotation written by the CI/CD job or the GitOps controller). The key is **application knowledge**, so it belongs in the config folder, never in code (`CLAUDE.md`, `ARCHITECTURE.md` rule 4):

```yaml
# services.yaml
deployed_at_keys: [deploy.example.com/at]   # annotations whose value is an RFC 3339 time; first found wins
```

The mechanism is ~15 lines (config field, schema via `make schema`, `docs/CONFIG.md`, the adapter copy of §4.2, rule 1 of §4.1). **Recommendation: leave it out of the first cut** and decide after seeing the controller-record source on a real cluster; the type has the slot (`DeployAnnotation`) so adding it later is not a redesign. It is an owner decision (§10).

## 7. Non-functional

| Aspect | Design |
|---|---|
| Requests, permissions | None added. The existing RBAC (`deployments`, `statefulsets`, `daemonsets`, `pods`, get/list/watch) is enough; this is checked in the QA by running with `huginn-reader` |
| CPU | `LastDeployment` runs only for the selected service's workloads at render time: O(pods of that service); no cache needed |
| Memory | One `time.Time` per workload (24 bytes) |
| Staleness | Refreshes with the watch like the rest of the preview; no new timer |
| Failure | A missing or unparsable value degrades to the next source, then to `no rollout record`; never an error and never a blank panel |
| Security | Times only; no secret, annotation values other than the configured time key are not read |

## 8. Test plan

- **Domain** (table-driven): every row of §5 and of the rule order of §4.1, including rollback built from pods with an old revision recreated, a lone old-revision pod during a rollout, empty revisions, deleted pods, zero pods.
- **Adapter**: conditions with each `reason` (`NewReplicaSetAvailable`, `ReplicaSetUpdated`, `ProgressDeadlineExceeded`, absent), `status` `True`/`False`/`Unknown`; StatefulSet/DaemonSet/CronJob leave `RolloutDone` zero.
- **TUI goldens**: every state of §4.4 at 80, 120 and 200+ columns (bottom and side panel), a service with two workloads, the `+n more` squeeze, a UTC and a non-UTC `Location`, a year boundary, a negative age. Existing preview goldens change by exactly one added section line; any other change is a regression.
- **Demo/e2e**: `--demo` shows each state; `internal/bootstrap` e2e over the demo cluster checks the section appears.
- **Gate**: `go test ./...`, `-race`, `golangci-lint run`, goldens reviewed.

## 9. Real-GKE verification (the full catalogue, V-1 to V-16, with fixtures, oracle, order and pass criteria, is in `M15-gke-qa.md` §2.6, §3, §4b and §9; this table is the summary the design needed)

Each of these checks an assumption this design makes. They are the reason source 1 is "to verify", not "known".

| ID | Action | Expected |
|---|---|---|
| V-1 | Deploy a new image of `payment-service`; read the preview during and after | `rolling out since` then `Nov … hh:mm` equal (within seconds) to `kubectl rollout status` completion and to the condition's `lastUpdateTime` |
| V-2 | **Wait 15+ minutes; scale 2→3→2; delete one pod; let an HPA act** | The controller-record time does **not** change. If it does, source 1 is wrong and the design changes (source 2 first, with the weakness stated) |
| V-3 | `kubectl rollout undo` | Moves to the rollback's completion |
| V-4 | `kubectl rollout restart` | Moves |
| V-5 | Drain the node (or delete every pod) of a Deployment | Source 1 unchanged; show the pods-only wording on a StatefulSet doing the same, to confirm the lower-bound behaviour |
| V-6 | Bad image (`ErrImagePull`) | `rolling out since … 0/2 updated`; the old completion time is not shown as current; recovery returns to a dated line |
| V-7 | StatefulSet rolling update; DaemonSet; CronJob | Pods source; `no rollout record` for the CronJob |
| V-8 | `huginn-reader` (namespace-scoped, no ReplicaSet/ControllerRevision rights) | Works unchanged |
| V-9 | `TZ` = UTC, `Asia/Tokyo`; local clock 5 min ahead | Zone shown; "just now", never negative |

## 10. Decisions needed from the owner

1. **Meaning:** time the rollout **completed** (recommended), or when it **started**? (Start is shown only while a rollout runs.)
2. **Placement:** a new DEPLOYED section (recommended) or appended to the WORKLOADS line (clips under ~100 columns).
3. **Annotation source (§6):** leave out of the first cut (recommended) or include now.
4. **Pods-only wording:** is `pods since …` clear enough, or would you rather hide the date when only the pods can give it?
5. **Services table:** leave `AGE` as is (recommended; it is the object's creation date) or add a column for the last deployment. Not designed here.
6. **Numbering:** this is M15.1 and its decision would be D-072; the QA's decision then becomes D-073.
