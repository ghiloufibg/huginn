# M4.2 — Head: the first lines of the logs  (status: proposed)

The windows load the **end** of the logs: the last 15 minutes … 2 days (keys `1`–`7`), or the last N lines (key `0`, tail). Nothing shows the **beginning**: how a container started, the configuration it printed, the first error before the crash loop. Today, the only way is `kubectl logs <pod> | head`.

This milestone adds a **head window**: the first N lines of each container.

## 1. What the user sees

### Key `9`: head
- `9` (AZERTY alias `ç`, new action `window_head`) loads the first `windows.head_lines` lines (default 500) of each container followed by the session.
- `huginn --since head` or `--since head:200` opens the logs on it. `windows.default: head` is accepted too.
- The window picker (`T`) lists it last, after tail: ` 9  head 500 lines`.
- `t` (next window) cycles through it: … `2d` → `tail` → `head` → `15m`.

### The view opens at the top
In every other window the view is pinned to the newest line at the bottom. A head is read from its first line, so:
- the cursor is on the **oldest** line and the view is not pinned (the `+N below` count shows how far the end is);
- `G` / `end` go to the last loaded line, as elsewhere;
- with `o` (newest first), the cursor is on the oldest line, now at the bottom.

### Status bar
- The mode chip is **`HEAD`**, in the style of `STOPPED`: a head does not follow.
- The window field says `head 500`.
- With `P` (previous instance), the chip stays `PREVIOUS INSTANCE` and the window field says `head 500 of the instance` (see §3).

### Following from a head
A head does not follow: new lines are not appended after its last line, which would leave a gap between line 500 and now.
- `f` in a head leaves the head: it opens the **default window** of `huginn.yaml` (tail if the default is head), following. The flash says `follow: back to 15m`.
- `space` (pause) does nothing in a head, as in `STOPPED`.

### Pods that appear during the session
The pod watch keeps running, as in `STOPPED`. A pod started during the session (a rollout, a restart after a crash) loads its own first N lines when it appears. During a rollout, this shows each new pod's startup, which is usually what a head is opened for. The new lines are placed by time, like the history of a new pod today.

### Empty view
`no log line in <repo>'s containers yet`, with the hints `0 last lines · esc back`.

## 2. What "the first lines" means in Kubernetes (shown to the user)

The first lines are the start of **what the node still keeps**, not necessarily the start of the container:

1. **Rotation.** The kubelet rotates container log files (on GKE, at about 10 MiB per file). The logs API serves the current file only, so for a chatty container the start may be gone. Huginn cannot fetch it; it **says so**:
   `payment-service-7f8f9-5cw8s: first line at 14:02, the container started at 09:10 (older lines rotated away on the node)`.
   The notice appears when the first line is more than 1 minute after the container's start.
2. **Restarts.** The current file belongs to the current instance. The start of the previous instance is the head of `P` (previous instance), see §3.
3. **Several pods and containers.** Each container gives its own first N lines, merged by time. For a Deployment whose pods started at different times, the view shows each pod's startup in turn, at its time. The pod column (`I`) tells them apart.

## 3. Head and previous instance

`P` reads the previous instance of the restarted containers (D-035). Today it reads the whole instance up to the buffer limit, and the window does not apply.

With head, `P` reads **the first N lines of the previous instance**: how the instance that crashed started. It is the most useful combination for a crash loop, and it costs N lines instead of up to 50 000 per container.

| Window | `P` off | `P` on |
|---|---|---|
| `15m` … `2d`, tail | unchanged | whole previous instance, as today |
| head | first N lines of the current instance | first N lines of the previous instance |

## 4. Configuration

`huginn.yaml`:

```yaml
windows:
  presets: [15m, 30m, 40m, 45m, 1h, 1d, 2d]
  tail_lines: 500
  head_lines: 500      # new: lines loaded per container by the head window (key 9)
  default: 15m         # may be head
```

| Key | Type | Default | Meaning |
|---|---|---|---|
| `windows.head_lines` | int | `500` | Lines loaded **per container** by the head window (key `9`). At least 1, at most `logs.buffer_lines`. |

- `presets` still accepts durations only (a head preset would be a duplicate of key `9`), like tail today.
- `windows.default: head` and `--since head[:N]` are accepted.
- After the change: `make schema`, `docs/CONFIG.md` §3, the CLI help and the README window list.

## 5. Design by layer

Nothing below reaches outside `internal/core` except through the existing ports. No new package; `internal/archtest` rules are unchanged.

### Domain (`internal/core/domain`)

- `TimeWindow` gets a third kind: `Head int`. Exactly one of `Since`, `Tail`, `Head` is set.
  - `IsHead()`, `String()` = `head 500`, `Label()` = `head`.
  - `ParseTimeWindow` accepts `head`, `head 200`, `head:200`, with a `defaultHead` argument next to `defaultTail`.
  - `DefaultWindowPresets(tail, head)` returns the head preset last, after tail. `NextWindow` needs no change.
  - `SelectWindow`: for a head, the first `Head` lines.
- `Container` gets `Started time.Time`, when the current instance started running. It is the reference of the rotation notice (§2). The Kubernetes adapter reads it from `state.running.startedAt` (or `state.terminated.startedAt`); the demo sets it from its instances.

### Port (`internal/core/ports/logs.go`)

`LogRequest` is unchanged in shape. Its contract is extended:
- `Window.Head > 0`: the first `Head` lines of the container (or of the previous instance with `Previous`), from the start of what the source keeps. `Follow` must be false; `SinceTime` and `Limit` do not apply.
- The source may stop reading after `Head` lines. The consumer never relies on getting fewer, and ignores the extra ones.

`LogQuery` is unchanged: `Window` carries the head. Its comment on `Previous` changes: "Window does not apply, except a head window".

### Application (`internal/core/app`)

- `LogSessions.Open`: a head window forces `Follow = false`, as `Previous` does.
- `tailer.request()`: with `Previous` and a head window, keeps the window (today it clears it). `Limit` is not set for a head.
- `tailer.history()` stops reading after `Head` lines and cancels the stream (its own child context), so a source that ignores the head still costs only N lines. This also makes the head exact for any future source.
- `decodeHistory` today keeps the **newest** `limit` lines of all containers (the buffer). For a head it keeps the **oldest**: it gets a `keep` argument (`newest` / `oldest`). The notice for the dropped lines says `newer lines not loaded: …` instead of `older lines of the window not loaded: …`. This happens when containers × `head_lines` exceeds `buffer_lines`.
- `retentionNotice` gets the head case: per container, the first line more than 1 minute after `Container.Started` gives the rotation notice of §2. Not for `Previous` (the previous instance's start time is not known).
- A pod that appears during a head session: its tailer loads its head and stops. `handleHistory` already treats a late history as live lines placed by time; nothing else changes.

### Kubernetes adapter (`internal/adapters/driven/kubernetes`)

`logOptions` for a head: no `tailLines`, no `sinceSeconds` / `sinceTime`, no `follow`, `timestamps: true` as always. The API then streams from the start of the current (or previous) log file. `stream.read` stops after `Head` lines and closes the body; closing the connection stops the kubelet, so a head of 500 lines over a 10 MiB file transfers a few buffers, not the file.

`limitBytes` is **not** used: it counts bytes, cuts the last line in the middle, and the line count already bounds the transfer.

### Demo adapter (`internal/adapters/driven/demo`)

`history` for a head: lines from `max(instance start, now - retention)` onward, the first `Head` of them, generating only what is kept, as it already does for tail. Its retention setting then produces the rotation notice in `--demo`, which gives the golden tests a case for it.

### TUI (`internal/adapters/driving/tui`)

- New action `ActWindowHead` (`window_head`), keys `9` and `ç`, group "Time and stream", description "head (first lines)". It appears in the help screen, the key bar hints of the window picker (`1…7 0 9 pick`), and can be remapped in `ui.yaml`.
- `windowKey` maps it to the head preset. The window picker lists it with its key.
- `setWindow` to a head: `follow` off, `tail` (pinned) off, cursor on the oldest line once the history has arrived.
- `f` in a head: switches to the default window (tail if the default is head) with follow on (§1).
- Mode chip `HEAD` (style `Chip`, like `STOPPED`) and window labels (§1, §3).
- Empty message of §1.

### Bootstrap and CLI

- `bootstrap.windows()` appends the head preset after tail, from `windows.head_lines`.
- `--since` accepts `head` and `head:N`. Its help and the README list them.

### Config (`internal/config`)

- `Windows.HeadLines int` (`yaml:"head_lines"`), default 500, validated `1 ≤ head_lines ≤ logs.buffer_lines`.
- `windows.default` accepts `head`; `presets` still rejects tail and head.

## 7. Documentation

- `docs/CONFIG.md` §3: `windows.head_lines`, `default: head`.
- README: key `9`, `--since head[:N]`, the head in the window list.
- `docs/DECISIONS.md` **D-039 Head window**, recording:
  - head is a window kind, not a flag: one key, one picker row, one `--since` value, no combination with durations;
  - per container, not per repository: the API has no global head, and per-container heads show each pod's startup;
  - no follow from a head; `f` goes back to the default window;
  - stop by line count and close the stream, no `limitBytes`;
  - the rotation limit is shown, not worked around (reading rotated files would need node access, which Huginn never has);
  - previous + head reads the start of the crashed instance.

## 8. Out of scope

- **"From the container start" beyond rotation**: rotated files are on the node only; Cloud Logging (the V2 log source of D-003) could serve them later through the same `LogSource` port.
- **A head of a time range** ("the first lines after 09:00"): `sinceTime` plus a line count would give it, but it needs a time input in the UI. It fits a later "go to time" feature.
- **Loading more after the head** (the next 500 lines): the API cannot start at line 501. A later version could re-read with a larger head and keep what is new.
