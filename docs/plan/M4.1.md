# M4.1 — Choose the containers of the logs, list standalone pods  (status: plan)

Two weaknesses left by M4 (D-037, "Not done"):
1. **Only application containers can be read.** `tab` and `S` select pods; the sidecars (`istio-proxy`, `vault-agent`…) are never streamed, and a pod's second application container can be told apart but not isolated.
2. **Pods that belong to no known workload are invisible**: a `kubectl run` debug pod, a Job created by hand, a ReplicaSet left behind (`--cascade=orphan`), pods of a controller Huginn does not know (Argo Rollouts, operators).

## 1. Containers: what the user sees

### Default: application containers
Nothing changes for the common case. The logs screen opens on the **application containers**, as today. Sidecars are the containers matched by `hide` in `containers.yaml`; init containers count as sidecars unless `show_init: true`.

### `A`: all containers on/off
`A` (new action `all_containers`) switches between:
- **app**: the application containers;
- **all**: every container of every pod, sidecars and init containers included.

The flash says `all containers (sidecars and init)` or `application containers`. In the status bar, `containers all` appears next to the pod scope when the mode differs from the default.

Switching reopens the session with the same window, filters, pod scope and levels. The history of the new containers is loaded, so it takes the time of a normal open, about 1–2 s. `R` (reset display) does not touch it: it changes which lines exist, not how they look.

### `S`: choose pods **and** containers
The selector gets a second section:

```
 Select pods and containers of payment-service                3 pods · 3 containers

 PODS
 [x] payment-service-7f8f9cc5-5cw8s   Healthy
 [x] payment-service-7f8f9cc5-6w4zx   Healthy
 [x] payment-worker-7d958895bb-df5hm  Healthy

 CONTAINERS
 [x] payment-service                  application
 [ ] istio-proxy                      sidecar · 2 pods
 [ ] migrate                          init · 2 pods
```

- **Pods × containers.** The two lists combine: the view shows the lines of the chosen containers in the chosen pods.
  - "The `istio-proxy` of every pod": select only `istio-proxy` in CONTAINERS.
  - "One pod's one container": select that pod and that container.
  - This covers both needs without a pod/container tree.
- **Container rows** are the distinct container names of the repository's pods: application first, then sidecars, then init containers. Each is labelled with its role and, when not in every pod, how many pods have it.
- **Selecting a sidecar or an init container** while in app mode switches the session to all containers (same reopen as `A`). Unselecting every sidecar does not switch back; `A` does.
- **Keys:** `space` toggles, `a` selects all of the section under the cursor, `/` selects by name pattern in that section, `enter` applies. These are the current keys, applied per section; `tab` moves between the two sections.

### `tab`: cycle, unchanged for pods
`tab` still cycles *all pods → pod 1 → pod 2 → … → all*. It keeps the container selection. The pod strip says which containers are in view when it is not the default (`containers: istio-proxy`).

### Lines
- When more than one container is in view for a pod, the pod column names the container (`5cw8s/istio-proxy`), as M4 already does for two application containers.
- **Sidecar names are dimmed**, so application lines stand out.
- Formats apply per container, as today (`formats/*.yaml`, `match.containers`). An `istio-proxy` access log without a format shows as plain text.

### Previous instance (`P`)
`P` follows the mode: with **all**, the previous instances of restarted sidecars are read too. An `istio-proxy` OOM kill is a classic case.

## 2. Containers: configuration

`containers.yaml` gains one key:

```yaml
version: 1
hide: [istio-proxy, vault-agent]  # sidecars: not shown in "app" mode
always_show: []
show_init: false
default_mode: app                 # app | all — the containers the logs screen opens on
```

| Key | Type | Default | Meaning |
|---|---|---|---|
| `default_mode` | `app` \| `all` | `app` | Containers streamed when a logs screen opens. `app`: application containers (everything not matched by `hide`, init containers only with `show_init`). `all`: every container. `A` switches during the session. |

The meaning of `hide` is clarified: it no longer means "never shown", it means **sidecar**. A sidecar is:
- not streamed in `app` mode;
- not counted in restarts, readiness or the version (unchanged).

There is also a one-run override flag: `--containers app|all`. It is validated like `--since`.

`make schema` regenerates `docs/schema/containers.schema.json`; `docs/CONFIG.md` documents the key; the lab and the examples show it.

## 3. Standalone pods: what the user sees

Pods that no known workload claims are listed as **standalone rows**, one row per group:

| Pods | Row | Kind shown |
|---|---|---|
| bare pod (no owner) | its pod name | `Pod` |
| owned by a Job that no CronJob made | the Job's name | `Job` |
| owned by a ReplicaSet whose Deployment does not exist | the ReplicaSet's workload name | `ReplicaSet` |
| owned by an unknown controller (Argo `Rollout`, an operator's CR) | the owner's name | its kind (`Rollout`) |

- **They go through the repository resolver like workloads, using the pods' labels.** A debug pod labelled `app.kubernetes.io/part-of: payment-service` joins the `payment-service` row (WL +1). Otherwise it is listed under WITHOUT REPO with its kind: `debug-shell (Pod)`, `one-off-migration (Job)`.
- **Status and WHY** come from its pods, as for any workload:
  - desired = its pods not being deleted;
  - ready = those ready;
  - a completed Job pod is healthy and "completed" (M4 pass-2 E4).
- **Logs, `P`, preview and events work as for a workload**: the session follows exactly the pods of the group, found by owner or, for a bare pod, by name.
- **`services.yaml` gains `standalone_pods: true | false`** (default `true`). Clusters full of finished one-off Jobs can turn them off.

## 4. Design (hexagonal, per docs/ARCHITECTURE.md)

### Domain
- `Pod.OwnerKind` (the controller kind the adapter resolved: `Deployment`, `CronJob`, `StatefulSet`, `DaemonSet`, `Job`, `ReplicaSet`, `Rollout`…; `""` for a bare pod).
- `Workload.Standalone bool`: a group of pods without a known workload. Its pods are identified by `OwnerName`/`OwnerKind`, or by pod name when bare, never by selector.
- `StandaloneWorkloads(ws []Workload, pods []Pod) []Workload`:
  - groups the pods no workload claims, using the same claim rule as today's pod index: owner name, else the selector for pods without an owner;
  - builds one synthetic workload per group: labels of its oldest pod, replicas from its pods, `Created` = oldest pod.
- `ContainerMode` (`ContainersApp`, `ContainersAll`) and `ContainerFilter.StreamContainers(p, mode)`:
  - app: `LogContainers` (application containers + blocking init containers, M4 pass-2 E3);
  - all: every container.
- `ContainerFilter.Role(c) (application | sidecar | init)` for the selector and the dimming.
- `ownedBy` moves to the domain as `Workload.Owns(p)`. It is standalone-aware, so the catalog and the log session share one claim rule. Today there are two slightly different ones.

### Ports
- `LogQuery.Containers ContainerMode`.
- `PodState.Roles map[string]ContainerRole` (role of each streamed container) for the view.
- `CatalogSnapshot` unchanged; standalone rows are `ServiceSummary` with `Standalone` set (shown with their kind).

### App
- **Catalog.** After indexing the pods, it builds the standalone workloads (when enabled) and passes them to the resolver with the others. Rows of standalone workloads are summarized from their group.
- **Log session:**
  - `workloadsOf` lists the pods of each namespace once, to build the same standalone workloads before resolving;
  - `podsOf` and `handlePod` use `Workload.Owns`;
  - tailers start for `StreamContainers(p, q.Containers)`.
- **Bootstrap:** `containers.default_mode` and `--containers` give `tui.Options.ContainerMode`; `services.standalone_pods` gives `Catalog.Standalone` and `LogSessions.Standalone`.

### Adapter (kubernetes)
- `ownerKind` next to `ownerName` (same derivation rules: a ReplicaSet with `pod-template-hash` means Deployment, a Job with a scheduled-time suffix means CronJob).
- **No new API permission**: pods are already listed per namespace.

### TUI
- **`logsScreen` state:**
  - `containerMode` (from options, toggled by `A`, sent in the query);
  - `containerScope map[string]bool` (nil = all streamed containers), applied in `inScope` together with the pod scope.
- **Pod selector:** two sections; applying a container scope that needs sidecars sets `containerMode = all` and reopens.
- **Rendering:** the pod column adds `/container` when several containers of a pod are in view; sidecar names use the dim ink.
- **Help, key bar, README:** `A` all containers, `S` pods and containers.

## 5. Tests
- **Domain:**
  - `StandaloneWorkloads`: bare pod, hand-made Job, orphan ReplicaSet, unknown controller;
  - a pod claimed by a Deployment selector is not standalone;
  - grouping by owner, replicas and status;
  - `StreamContainers` in both modes; `Role`.
- **App:**
  - catalog lists standalone rows, and resolves a labelled debug pod into its repository;
  - disabled by config;
  - log session of a standalone row follows exactly its pods;
  - `LogQuery.Containers = all` streams sidecars;
  - claim rule shared (a bare pod matching a Deployment selector stays with the Deployment).
- **TUI:**
  - selector with two sections (golden);
  - container scope filters lines without reopening;
  - choosing a sidecar in app mode reopens in all mode, keeping window, filters and pod scope;
  - `A` toggles and flashes;
  - sidecar names dimmed and the pod column names the container (golden);
  - status bar `containers all`.
- **Config:** `default_mode` validated (`app|all`, with a suggestion on typos); `standalone_pods` bool; examples load; schema regenerated.
- **Adapter:** `ownerKind` derivation; bare pod `""`.
- **Lab and e2e:**
  - `deploy/lab/extra.yaml` already has a bare pod case (`kubectl run`) and sidecars (`istio-proxy`, `traffic`);
  - `e2e.sh` checks that `A` shows `istio-proxy` lines in `payment-service` and that a bare pod appears as a row, and opens its logs.

## 6. Decision to record (D-038)
- **Containers:**
  - the logs screen opens on the application containers (configurable, `default_mode`);
  - `A` streams all containers;
  - `S` selects pods × containers;
  - `hide` means "sidecar", not "never".
  - Sidecars are not streamed by default because they are often the chattiest containers (mesh access logs). Streaming them always would fill the buffer and evict the application's lines.
- **Standalone pods:**
  - they become synthetic workloads, so every screen (resolver, status, logs, `P`, events) works on them unchanged;
  - grouped by owner, and by name when bare;
  - shown by default, and can be turned off.

## 7. Risks
- **Buffer pressure in all mode.** A mesh sidecar can log more than the application. The buffer is shared, so in all mode old application lines are evicted sooner. The status bar already reports lines skipped; the D-038 note says so.
- **Many standalone rows.** Clusters with hundreds of finished one-off Jobs (no TTL) get many rows. They are healthy, so they sort to the bottom, and `standalone_pods: false` removes them.
- **Label resolution of debug pods.** A `kubectl debug --copy-to` pod keeps the app's labels and joins its repository. This is wanted: it is that app's pod. It is marked `Pod` in the preview.
