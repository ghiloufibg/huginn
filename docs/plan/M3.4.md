# M3.4 — Profiles: all application knowledge comes from files the user provides  (status: design)

## Goal (open/closed)
Huginn is **closed for modification, open for extension**. Supporting a new company, cluster, log format, line layout, sidecar or repository convention must mean **writing or changing a file**, never changing the TUI's code. The user brings that knowledge in a **profile**, a folder or file given at launch. Huginn ships **no data about any application**. It ships only:
- generic mechanisms (decoders, scanners, resolvers, renderers, secret providers);
- UI behaviour;
- Kubernetes semantics (pod status, the WHY column, rollouts).

## 1. Where things stand today
A lot is already configuration (`config.yaml`): environments, repo mappings, label keys, manifest globs, JSON field paths, the container denylist and the keymap. What still lives **in the code**:

| Knowledge | Where it lives today | Problem |
|---|---|---|
| Environment names `dev/rec/prprd/prd`, namespaces `app-*`, `default_env: rec` | `config/defaults.go` | Our company's data, used when no file is given |
| The `logstash` format (field paths, hidden `kubernetes.*`) | `config/defaults.go` | Same |
| Label keys, the Kustomize overlay glob | `config/defaults.go` | Same |
| Sidecar denylist (istio, vault-agent…) | `config/defaults.go` | Same |
| The **line layout** (Spring Boot compact/full) | `adapters/driven/springlayout` (Go) | A new layout (Node, Go, nginx…) needs code |
| The columns `time/level/thread/class`, their picker keys and the `c` cycle order | `tui/columns.go` | Adding a column (for example a trace id) needs code |
| "Own frames" in stack traces (java., org.springframework.…) | `tui/zoom.go` | Only works for JVM stacks |
| Time-window presets (15m … 2d) | `domain/timewindow.go` | Fixed |
| One log format for everything | `logs.format` | A repository that logs differently cannot be read |

## 2. The profile

### 2.1 Launching
```
huginn --profile ~/work/acme-huginn           # a folder
huginn --profile ./acme.yaml                  # or a single file
HUGINN_PROFILE=~/work/acme-huginn huginn rec  # or the environment variable
```
The profile is looked for in this order:
1. `--profile`;
2. `HUGINN_PROFILE`;
3. `profile:` in the personal settings (§2.4), so it is remembered;
4. otherwise, **no profile, no start**: Huginn exits with a short message showing how to create one (`huginn profile init`). There are no hidden built-in defaults.

`--demo` uses a demo profile embedded in the binary. It has exactly the same format as a user's profile, which proves the TUI needs nothing else. `--config` stays as an alias of `--profile` for one version.

### 2.2 Folder layout (suggested, not imposed)
A profile is **a folder of YAML files**, all read and merged. The file names are free; only their contents count. A team versions it in its own git repository, for example `acme/huginn-profile`:

```
acme-huginn/
  profile.yaml            # name, version, default environment
  environments.yaml       # clusters, contexts, namespaces
  services.yaml           # workload → repository: labels, explicit mappings, manifests
  containers.yaml         # which containers are application containers
  formats/
    spring-logstash.yaml  # how to read a JSON line (fields, levels, hidden fields)
    nginx-access.yaml     # how to read a text line (regex with named groups)
  layouts/
    spring.yaml           # how to draw a line: columns, templates, stack rules
  windows.yaml            # time-window presets
```

Every file starts with a header that tells what it contains and which version of the format it follows:
```yaml
apiVersion: huginn/v1
kind: LogFormat          # Profile | Environments | Services | Containers | LogFormat | Layout | Windows
```
Merge rules:
- **Collections are merged by name**: `environments.rec`, `formats.spring-logstash`, `layouts.spring`. The same name defined in two files is an error, and the error names both files.
- **Unique sections** (`Profile`, `Containers`, `Windows`) may appear only once.
- Validation is strict and reports every problem at once (unknown keys with a suggestion, missing references such as a layout that names an unknown format, invalid regexes). Each problem gives `file:line`.

### 2.3 What each kind contains

**Profile**: identity and defaults.
```yaml
apiVersion: huginn/v1
kind: Profile
name: acme
default_env: rec
repos_root: ~/work/repos        # optional, overridable in the personal settings
```

**Environments**: the same fields as today.
```yaml
kind: Environments
environments:
  rec: { context: gke_acme_europe-west1_main, namespaces: [app-rec] }
  prd: { context: gke_acme_europe-west1_main, namespace_from: "sops:overlays/prd/config.env#K8S_NAMESPACE", production: true }
```

**Services**: how a workload is attached to a repository. These are today's `repos`, `resolver` and `manifests` sections.
```yaml
kind: Services
resolver: { order: [config, labels, manifests], label_keys: [app.kubernetes.io/part-of, app] }
manifests: { scanner: kustomize, overlay_glob: "**/overlays/{env}", files: [kustomization.yaml] }
repos:
  - { name: payment-service, workloads: [{ env: rec, name: payment-worker }] }
```

**Containers**: sidecars.
```yaml
kind: Containers
denylist: [istio-proxy, istio-init, vault-agent, cloud-sql-proxy]
allowlist: []
include_init: false
```

**LogFormat**: how to **read** a line. A profile can hold several formats, and each is selected by rules.
```yaml
kind: LogFormat
name: spring-logstash
decoder: json-fields                     # json-fields | regex | plain
match:                                   # which containers use this format (first matching format wins)
  repos: ["*"]                           # glob on the repository
  containers: ["*"]                      # glob on the container
  labels: {}                             # labels the pod must carry
fields:
  timestamp: ["@timestamp", time]
  level:     [level, severity]
  logger:    logger_name
  thread:    thread_name
  message:   message
  stack:     stack_trace
  trace_id:  [traceId, trace_id]
levels:                                  # the text of each level in these logs (case-insensitive)
  error: [ERROR, FATAL, "50"]
  warn:  [WARN, WARNING, "40"]
  info:  [INFO, "30"]
  debug: [DEBUG, TRACE, "20", "10"]
hidden: ["kubernetes.*", "@version", host]  # shown only in zoom
layout: spring                           # how to draw its lines (see Layout)
```
```yaml
kind: LogFormat
name: nginx-access
decoder: regex                           # for non-JSON lines: named groups = fields
pattern: '^(?P<remote>\S+) - - \[(?P<timestamp>[^\]]+)\] "(?P<message>[^"]*)" (?P<status>\d{3})'
time_layout: "02/Jan/2006:15:04:05 -0700"
level_from: { field: status, map: { "5..": error, "4..": warn, "*": info } }
match: { containers: [nginx] }
layout: access
```

**Layout**: how to **draw** a line. The columns are **declared by the profile**, not by the TUI. Their order is the order of the `c` cycle, and `key` is their letter in the `C` picker.
```yaml
kind: Layout
name: spring
columns:                          # before the message, in this order
  - { name: time,   key: t, template: "{time}" }
  - { name: level,  key: l, template: "{level|pad:5}",        style: level }
  - { name: thread, key: h, template: "[{thread|pad:15}]",    style: thread, hide_below: 140 }
  - { name: class,  key: c, template: "{logger|abbrev:40}",   style: logger, hide_below: 110 }
  - { name: trace,  key: x, template: "{trace_id|tail:8}",    style: dim,    shown: false }   # a new column, no code
message: ": {message}"
extra_fields: true                # visible fields as key=value after the message
full:                             # the zoom layout
  template: "{time|date} {level|pad:5} {pid} --- [{app}] [{thread|pad:15}] {logger|abbrev:40} : {message}"
stack:
  own_frames_exclude: ["java.", "javax.", "jdk.", "jakarta.", "org.springframework.", "org.apache.", "io.netty."]
```
- **Template language**: `{field}` where field is a standard field (`time level logger thread message trace_id app pid`) or any path in the line (`{field:http.status}`). Filters are chained with `|`: `pad:N`, `right`, `abbrev:N` (Logback-style package shortening), `tail:N`, `upper`, `date`, `default:"-"`. An empty field removes the whole column from the line, literal text included.
- **Styles** come from the theme through **roles** (`level`, `thread`, `logger`, `dim`, `timestamp`, `message`), so a layout never picks colours and stays readable with `NO_COLOR`.
- `hide_below` replaces the width thresholds of automatic narrowing (140/110) that are fixed in code today.
- `c`, `C`, `z`, `R`, filters and zoom work unchanged on the columns of the layout. The pod column (`I`) stays the TUI's own, because it is Kubernetes, not the application.

**Windows**: the presets for keys 1…7 and 0.
```yaml
kind: Windows
presets: [15m, 30m, 40m, 45m, 1h, 1d, 2d]
tail: 500
default: 15m
```

### 2.4 Personal settings (separate from the profile)
What belongs to the **person**, not the team, stays in `~/.config/huginn/settings.yaml`: `profile:` (the path remembered), `theme`, `keymap`, `key_bar`, the chosen columns, `repos_root`, `buffer_lines`. The profile never contains these settings and the settings never contain application data. **One team profile is shared by everyone; each person has their own settings.**

## 3. Tools that come with it
- `huginn profile init <folder>`: writes a complete, commented starter profile (our current values become **the example**, no longer the defaults).
- `huginn profile validate [<folder>]`: strict validation that lists every problem with `file:line`. Useful in the profile repository's CI.
- `huginn profile show`: the effective merged profile, each value annotated with the file it comes from.
- `huginn profile test-line <format> '<line>'`: decodes and draws a line with a format and its layout. This is the quickest way to tune a new format without a cluster.
- **Published JSON schema** (`docs/profile.schema.json`, one definition per `kind`): IDE autocompletion and validation (the `# yaml-language-server: $schema=…` header is written by `init`).

## 4. Architecture (what changes in the code, once)
- `internal/config` becomes the **profile loader**: it reads a folder, dispatches on `kind`, merges, checks references, and produces the same structs as today (the adapters barely change).
- `config/defaults.go` **loses all application data**. Only neutral technical values remain (buffer size, timeouts, theme).
- **New generic adapters** (written once, then driven by files):
  - `logformat/regex`: decoder with named groups;
  - `layout/template`: the template renderer. It replaces `springlayout`, whose two layouts become `layouts/spring.yaml` in the demo profile and in `profile init`.
- **Format selection per container**: a `FormatSelector` port in the core, `(repo, container, labels) → format`. It is implemented by the loader from the `match` rules. The log session asks for the decoder and renderer of each container, instead of one global format.
- **Columns are data**: the TUI receives the list of columns (name, key, role, `hide_below`, shown by default) from the layout. The picker, `c` and the status bar are built from that list. The `ColTime/ColLevel/…` constants disappear from `ports`.
- The **own frames** list leaves `zoom.go` and comes from the layout (`stack.own_frames_exclude`).
- `archtest`: new rule so that no package of `core` or `tui` contains application data (a list of forbidden strings: `org.springframework`, `istio`, `app-rec`…). This keeps the rule over time.
- Adding a **new kind of decoder, scanner or secret provider** (for example `protobuf`, `helm`, `vault`) stays code, but only as a new adapter registered in the existing `Registry`. The TUI and the core are never touched.

## 5. Compatibility
- A current `config.yaml` (a single file without `kind`) is still read as a **one-file profile** plus personal settings, with a warning telling you to run `huginn profile init --from config.yaml`, which splits it into files. It is removed in the next milestone.
- The demo keeps working through its embedded profile, and its goldens do not change: same layout, now described in YAML.

## 6. Tests
- Loader: folder merge, name collisions between two files, unknown `kind`, broken references, `file:line` errors, a one-file profile, the old `config.yaml`, no profile → clear message.
- Format selection: glob rules on repo, container and labels, fallback on `plain`, a pod with two containers in two formats.
- Template: every filter, an empty field removing the column, `abbrev` identical to today's Spring layout (the springlayout goldens must stay the same byte for byte), `NO_COLOR`.
- Regex decoder: nginx access line, level by status, time layout.
- TUI: columns declared by the layout (a `trace` column added and removed by `c` and `C` without code), `hide_below`.
- `profile validate`, `show` and `test-line` in CLI tests; the schema is regenerated by `make schema` and checked in CI.
- archtest: no application data in `core` or `tui`.

## 7. Decisions to record (D-030)
Profile = team folder of YAML files typed by `kind`, merged by name. Personal settings separate. No built-in application data, no start without a profile (except `--demo`). Layouts are templates and their columns are data. Format chosen per container by `match` rules. Regex decoder for text logs. `--config` becomes an alias for one version.
