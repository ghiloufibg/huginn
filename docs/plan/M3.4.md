# M3.4 — A config folder the user provides: the TUI holds no application data  (status: done)

## Goal (open/closed)
Huginn is **closed for modification, open for extension**. Everything it knows about **your** applications comes from a **config folder** that you provide at startup:
- environments and namespaces;
- how a workload maps to a repository;
- which containers are sidecars;
- how a log line is read;
- how a log line is drawn.

Supporting another company, cluster or log format means **writing files**, never changing the TUI.

The TUI stays lightweight. It only:
1. reads the folder at startup;
2. checks it against the structure documented in `docs/CONFIG.md`;
3. starts, or prints **every** error and exits.

There are no profile commands, no generators and no built-in application data.

## 1. Starting
```
huginn --config ~/work/acme-huginn rec
HUGINN_CONFIG=~/work/acme-huginn huginn rec
huginn rec                     # uses ~/.config/huginn/ (the OS config directory)
huginn --demo                  # uses the demo folder embedded in the binary
```
- **Where the folder is taken from, in order**: `--config`, then `HUGINN_CONFIG`, then `<user config dir>/huginn/`.
- **No folder found**: Huginn prints the expected structure, points to `docs/CONFIG.md` and exits with code 2.
- **The single-file `config.yaml` is dropped** (this is a prototype, so there is no migration period).
- **The `huginn config example|validate` subcommands are removed.** Startup already validates, and `examples/config/` is the example.

## 2. The folder structure (fixed names)
```
acme-huginn/
├── huginn.yaml             required   version, default environment, time windows
├── environments.yaml       required   environments: kube context, namespaces, production flag
├── services.yaml           required   how workloads map to repositories
├── containers.yaml         optional   which containers are sidecars (default: none hidden)
├── ui.yaml                 optional   theme, keymap, key bar (personal choices)
├── formats/                required   at least one file; one log format per file
│   ├── spring-json.yaml
│   └── nginx.yaml
└── layouts/                required   at least one file; one line layout per file
    └── spring.yaml
```
- **File names are fixed.** Each file has one role, so the documentation is one section per file.
- **Names come from file names.** A format or layout is named after its file (`formats/spring-json.yaml` defines the format `spring-json`). There are no duplicate names to manage.
- **Anything unexpected is an error.** An unknown file or folder (for example `enviroments.yaml`) is reported with a suggestion ("did you mean environments.yaml?"), so a typo is never silently ignored.
- **Every file starts with `version: 1`.** The structure can then change later while old folders are still recognised.
- **Secrets are referenced, never copied.** A value `sops:<file>#<key>` is read through sops, as today.

## 3. The contents, file by file
Summary below. The full reference for every key is `docs/CONFIG.md`: type, required or optional, default, meaning and example.

### `huginn.yaml`
```yaml
version: 1
default_env: rec                  # must be a key of environments.yaml
repos_root: ~/work/repos          # optional: where to read the repositories' manifests
windows:                          # keys 1…7 then 0 (tail); optional, these are the defaults
  presets: [15m, 30m, 40m, 45m, 1h, 1d, 2d]
  tail_lines: 500
  default: 15m
logs:
  buffer_lines: 50000             # optional
```

### `environments.yaml`
```yaml
version: 1
environments:
  rec:
    context: gke_acme_europe-west1_main      # kubeconfig context (empty = current context)
    namespaces: [app-rec]
  prd:
    context: gke_acme_europe-west1_main
    namespace_from: sops:overlays/prd/config.env#K8S_NAMESPACE   # instead of namespaces
    production: true                                            # red banner
```

### `services.yaml`
```yaml
version: 1
resolve: [explicit, labels, manifests]      # order of the rules; the first match wins
label_keys: [app.kubernetes.io/part-of, app]
manifests:                                  # only if "manifests" is in resolve
  overlay_glob: "**/overlays/{env}"
  files: [kustomization.yaml]
explicit:                                   # only if "explicit" is in resolve
  - repo: payment-service
    workloads:
      - { env: rec, name: payment-worker }  # kind: Deployment by default
```

### `containers.yaml` (optional)
```yaml
version: 1
hide: [istio-proxy, istio-init, vault-agent, cloud-sql-proxy]   # names or image substrings
always_show: []
show_init: false
```

### `formats/<name>.yaml`: how to **read** a line
Several formats can coexist. Each container gets the **first format whose `match` applies**, in file name order. A format without `match` applies to everything and should come last (for example `zz-default.yaml`).
```yaml
version: 1
decoder: json                     # json | regex | plain
match:                            # optional; every listed condition must hold
  repos: ["*"]                    # globs on the repository
  containers: ["*"]               # globs on the container name
fields:                           # candidate JSON paths; the first one present wins
  time:     ["@timestamp", time]
  level:    [level, severity]
  logger:   logger_name
  thread:   thread_name
  message:  message
  stack:    stack_trace
  trace_id: [traceId, trace_id]
levels:                           # how each level is written in these logs (case ignored)
  error: [ERROR, FATAL]
  warn:  [WARN, WARNING]
  info:  [INFO]
  debug: [DEBUG, TRACE]
hidden: ["kubernetes.*", "@version", host]   # never on the stream, only in zoom
layout: spring                    # a file of layouts/
```
Text logs (`decoder: regex`) name their fields through **named groups**:
```yaml
version: 1
decoder: regex
match: { containers: [nginx] }
pattern: '^(?P<remote>\S+) \S+ \S+ \[(?P<time>[^\]]+)\] "(?P<message>[^"]*)" (?P<status>\d{3})'
time_format: "02/Jan/2006:15:04:05 -0700"   # Go reference layout
level_from: { field: status, map: { "5*": error, "4*": warn, "*": info } }
layout: access
```

### `layouts/<name>.yaml`: how to **draw** a line
The layout **declares its columns**. Their order is the order of the `c` key, `key` is their letter in the `C` picker, and `hide_below` hides them on narrow terminals. The pod column is not declared here: it belongs to Kubernetes, and `I` controls it.
```yaml
version: 1
columns:
  - { name: time,   key: t, show: "{time}" }
  - { name: level,  key: l, show: "{level|pad:5}",         role: level }
  - { name: thread, key: h, show: "[{thread|pad:15}]",     role: thread, hide_below: 140 }
  - { name: class,  key: c, show: "{logger|abbrev:40}",    role: logger, hide_below: 110 }
  - { name: trace,  key: x, show: "{trace_id|last:8}",     role: dim,    visible: false }
message: ": {message}"
zoom: "{time|date} {level|pad:5} {pid} --- [{app}] [{thread|pad:15}] {logger|abbrev:40} : {message}"
stack:
  framework_prefixes: ["java.", "jdk.", "jakarta.", "org.springframework.", "org.apache.", "io.netty."]
```
**Mini template language**:
- `{field}` is a standard field (`time level logger thread message trace_id app pid`), or any JSON path or regex group with `{field:http.status}`.
- Filters: `pad:N`, `right`, `abbrev:N` (Logback-style package shortening), `last:N`, `upper`, `date`, `default:x`.
- An empty field removes its whole column, surrounding text included.
- `role` picks a colour from the theme (`level thread logger dim time message`). The files never contain colours.

### `ui.yaml` (optional)
```yaml
version: 1
theme: light                      # light | accessible | classic | none
key_bar: compact                  # compact | full | hidden
keymap: { follow: [f, ctrl+l] }   # action → keys
```

## 4. Error reporting
Everything is checked **before** the TUI opens, and **all** problems are listed at once, sorted by file and line, one per line:
```
huginn: the config folder ~/work/acme-huginn has 4 errors (see docs/CONFIG.md):
  environments.yaml:7:5    prd: set namespaces or namespace_from, not both
  services.yaml:2:1        unknown key "resolver" (did you mean "resolve"?)
  formats/nginx.yaml:5:10  pattern: missing group (?P<message>…)
  layouts/spring.yaml:4:3  columns[2]: key "l" already used by column level
```
Exit code 2, and the TUI does not open.

What is checked:
- **Syntax:** YAML syntax, `version`, unknown keys (with a suggestion), types and allowed values.
- **Required items:** required files and keys are present.
- **Cross-file references:** `default_env`, a format's `layout`, the environments named in `explicit`.
- **Formats:** regexes compile, and a regex format has a `message` group; windows and durations parse.
- **Layouts:** column names and keys are unique, and templates are valid.
- **Files:** no unexpected files.
- **Secrets:** a `sops:` reference that cannot be read is reported at startup with its file and line.

## 5. Documentation for anyone writing a folder
- **`docs/CONFIG.md`, the reference**:
  - the folder tree;
  - one section per file with a table (key, type, required, default, description);
  - the template language;
  - the format selection rules;
  - the list of errors and how to fix them;
  - a "write your folder in 15 minutes" walkthrough, starting from a real log line: pick the JSON paths, write the format, write the layout, check at startup.
- **Worked examples, validated in CI:**
  - `examples/config/` is the complete Spring Boot + logstash case (ours, now an example rather than a default) and also serves as the demo folder;
  - `examples/config-node/` covers Node.js JSON logs (pino: `level: 30`, `msg`, `time` in ms);
  - `examples/config-nginx/` covers text logs with the regex decoder.
- **Editor autocompletion:** a JSON schema per file (`docs/schema/*.json`), generated by the existing `make schema`. Each example file starts with `# yaml-language-server: $schema=…`. This is a file, not a tool.
- `docs/ARCHITECTURE.md` gets one sentence: application knowledge enters only through the config folder.

## 6. What changes in the code (once)
- **`internal/config` reads a folder:**
  - fixed file names, strict decoding keeping line numbers, all errors collected;
  - it produces the structs the adapters use today;
  - `defaults.go` keeps only neutral technical values (buffer size, windows, theme).
- **Removed from the code, now in `examples/config/`:**
  - environments `dev/rec/prprd/prd` and `app-*`;
  - the `logstash` format;
  - label keys;
  - the sidecar list;
  - the Spring layout;
  - the Java frame prefixes.
- **The demo folder** is `examples/config/`, embedded in the binary with `go:embed`. The demo goldens must not change.
- **New generic adapters:**
  - `logformat/regex`, the regex decoder;
  - `layout/template`, the template renderer, which replaces `springlayout`. The Spring layout becomes `examples/config/layouts/spring.yaml`, and the existing reference lines must match byte for byte.
- **A format per container:** a `FormatSelector` port, `(repo, container) → decoder + renderer`, built from the `match` rules. The log session asks it for each container.
- **Columns are data:** the TUI receives the columns of the layout (name, key, role, `hide_below`, visible). The `C` picker, `c`, `R` and the status bar are built from that list. The `ColTime/ColLevel/…` constants disappear.
- **archtest:** a rule forbids application data in `core` and `tui` (a list of strings such as `org.springframework`, `istio`, `app-rec`…).
- **CLI:** `--config` takes a folder, and the `config` subcommands are removed.

## 7. Tests
- **Loading a folder:**
  - a missing file;
  - an unexpected file;
  - an unknown key with a suggestion;
  - a bad type;
  - broken references;
  - `file:line:column` positions;
  - all errors reported in one run;
  - exit code 2 and no TUI.
- **The examples load without errors:** `examples/config`, `config-node` and `config-nginx`, checked in CI.
- **Format selection:** glob rules, order by file name, a pod whose two containers use two formats, fallback to `plain` when nothing matches.
- **Regex decoder:** an nginx line, the level derived from the status, the time format.
- **Templates:**
  - every filter;
  - an empty field removing its column;
  - the Spring layout identical to today (the springlayout goldens are kept);
  - `NO_COLOR`.
- **TUI:** a `trace` column added by the layout and cycled by `c` and `C` without code; `hide_below`.
- **archtest:** no application data in `core` or `tui`.

## 8. Decision to record (D-030)
- The config folder has fixed file names and is validated at startup.
- Every error is listed with `file:line` and the TUI does not start.
- The code holds no application data; `examples/config/` is the reference and the demo.
- Formats are chosen per container through `match`; layouts are templates whose columns are data; text logs use a regex decoder.
- No profile tooling, and the single-file `config.yaml` is removed.

## As built
- One code commit (the loader, the removal of built-in data, decoders, layouts and the TUI columns change the same types) and one documentation commit.
- Templates and the keymap are validated by their adapters; their problems are added to the same report as the loader's, with positions.
- A column is left out when all its fields are empty, unless a `default` filter is used. Lines no format could parse keep only the columns that use nothing but `{time}`.

- `--demo` uses the embedded `examples/config` unless `--config` is given. The demo cluster plays its rollout in `default_env`.
