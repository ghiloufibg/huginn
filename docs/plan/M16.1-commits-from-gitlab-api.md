# M16.1 — Commit details from GitLab's API only; git removed  (status: design, owner decision of 2026-11-21 applied; one point open §9)

**Question (owner, 2026-11-21):** can Huginn read the commit message and the "not deployed" count **from the remote directly**, without fetching, in case the local clone is stale; otherwise, use the GitLab API it already calls, and not rely on git commands at all?

**Decision (owner, 2026-11-21): GitLab's API only. No second mode: git is removed from the feature** (the `gitcli` adapter, Huginn's copies of the remotes, every git process).

This is a design only. Nothing below is implemented. GitLab API facts that could not be checked here are marked **to verify** and join the QA of [`M16-qa.md`](M16-qa.md).

## 1. Why the API: git cannot read a remote without fetching

| Way | What it can give | Verdict |
|---|---|---|
| `git ls-remote <url>` | Branch and tag names with their commit ids. **No message, no author, no count**: the git protocol only sends refs and objects | Not enough |
| `git archive --remote` | Files of a tree, not history; GitLab does not serve it over HTTPS, and not over SSH by default | Not usable |
| `git fetch` (M16 as built) | Everything, after downloading commits into Huginn's own copy (`~/.cache/huginn/git`), with git, SSH or HTTPS credentials and disk | **Removed** |
| **GitLab REST API** (same token, `read_api`) | Message, author, dates, tag → commit, counts between two commits, per path | **Chosen** |

For the record: M16 as built did not read the possibly stale local clone, except as a fallback. It kept its own copy of the remote, fetched at most every minute. What this change removes is git itself: the processes, the copy on disk, the SSH or HTTPS credentials, and the clone fallback.

## 2. What changes

| | M16 as built | M16.1 |
|---|---|---|
| Commit message of a found release | From GitLab's deployment | Unchanged |
| Commit message of a guess (image tag, git tag) | `git log` / `git rev-parse` | GitLab commits and tags API (§3) |
| "N not deployed", on the trunk or not | `git rev-list` on Huginn's copy | GitLab API (§3) |
| Finding the GitLab project of a repository | `git remote get-url` on the clone | The clone's `.git/config` **read as a file**, no git process (§4.2) |
| Needs git installed, an SSH key or credential helper, disk | Yes | **No**: only the token Huginn already has |
| Offline (VPN off) | Counts from the clone, `(local, may be stale)` | `GitLab unreachable`; a release already found keeps its commit and subject for the session; no count |
| `.env` git-ignored check at start | `git check-ignore` | Read without git (§7) |

Unchanged: the owner's deployment search (digest in the promote job's log), the COMMIT line and its layout, the per-frame cost, `environments.yaml` `gitlab:`, the token, the monorepo rules.

## 3. GitLab calls

All `GET`, REST v4, same client, token, redirect policy and error classification as the deployment search (`adapters/driven/gitlab`).

| Need | Request | Reads |
|---|---|---|
| The trunk's name (`origin/HEAD`) | `GET /projects/:id` | `default_branch`; cached an hour |
| The trunk's tip | `GET /projects/:id/repository/branches/:branch` | `commit.id`; the cache key of the counts (§6) |
| **Not deployed** | `GET /projects/:id/repository/commits?ref_name=<sha>..<branch>&per_page=1` | the `X-Total` header = the count. **To verify:** that `ref_name` accepts a revision range on the owner's GitLab version, and that `X-Total` is sent |
| **On the trunk** | `GET /projects/:id/repository/merge_base?refs[]=<sha>&refs[]=<branch>` | on the trunk when the merge base **is** the running commit |
| Not deployed, **monorepo workload with `paths`** | the commits request with `&path=<path>`, once per path, listing ids (`per_page=100`), counting the union | exact up to 100 per path, then `100+` |
| A commit (a guess, or a deployment without a subject) | `GET /projects/:id/repository/commits/:sha` | `id`, `title`, `author_name`, `committed_date`. **To verify:** that an abbreviated id from an image tag is accepted |
| Git tag fallback | `GET /projects/:id/repository/tags/:tag` (then `v<tag>`) | `commit.id` |

`X-Total` is not sent when a list is very large (GitLab drops it for performance; **to verify** the limit). The line then says `10000+ not deployed`, never a wrong number. If revision ranges are refused (an old GitLab), the count uses `GET /projects/:id/repository/compare?from=<sha>&to=<branch>` and counts its `commits`. That answer also carries diffs and is capped by GitLab, so it is shown as `N+` when capped.

## 4. Ports and adapters

### 4.1 Port: `CommitLog` becomes project-based

```go
// CommitLog reads commits of a hosted project. Read only. Errors are
// domain kinds (ErrUnauthorized, ErrForbidden, ErrNotFound, ErrUnreachable).
type CommitLog interface {
    // Commit resolves sha, possibly abbreviated; ErrNotFound when unknown.
    Commit(ctx context.Context, p ReleaseProject, sha string) (Commit, error)
    // Tag returns the commit a tag points to; ErrNotFound when none.
    Tag(ctx context.Context, p ReleaseProject, tag string) (sha string, err error)
    // Trunk resolves a reference to a branch name and its tip: "HEAD" is
    // the project's default branch.
    Trunk(ctx context.Context, p ReleaseProject, ref string) (branch, tip string, err error)
    // Count returns how many commits of branch sha lacks (only those
    // touching paths, when given; capped says the number is a lower
    // bound), and whether sha is on branch.
    Count(ctx context.Context, p ReleaseProject, sha, branch string, paths []string) (behind int, capped, onBranch bool, err error)
}
```

`RemoteURL`, `Refresh`, `GitRepo` and the `stale` results are removed. `domain.TrunkCount.Stale` goes, and `Capped` is added (shown as `N+`).

### 4.2 Finding the project: `.git/config` read as a file

A small function, behind a new method on the existing `ports.LocalFiles` (the adapter that already reads local files with bounds):

```go
// GitRemote returns the URL of remote in the clone at dir, read from its
// .git/config (a worktree's or submodule's ".git" file is followed). No
// git process. ErrNotFound when dir is not a clone or has no such remote.
GitRemote(ctx context.Context, dir, remote string) (string, error)
```

It reads the `[remote "<name>"] url = …` entry. `include` and `includeIf` sections are not followed (**to verify** that the owner's clones do not set their remote that way), and `insteadOf` rewrites are applied when they are in the same file. `domain.ParseGitRemote` is unchanged. Whether to also allow a `project:` template, so no clone is needed at all, is the one open point (§9).

### 4.3 Adapters

- **`adapters/driven/gitlab`**: gains `Commits`, implementing `ports.CommitLog` with the requests of §3, on the same `Client`.
- **`adapters/driven/gitcli`**: **deleted**, with its tests. `Ignored` (the `.gitignore` check) is replaced (§7).
- **`adapters/driven/localfiles`**: gains `GitRemote`.
- **`demo`**: `demo.Git` becomes `demo.Commits`, the same synthetic history behind the new port.

### 4.4 App (`core/app/releases.go`)

Changes only where it used git: the project comes from `Files.GitRemote` and `ParseGitRemote`; no refresh step; `compare_ref` is resolved once with `Trunk` (`origin/HEAD` → `HEAD`, `origin/<b>` → `<b>`); the counts are cached by `(project, sha, tip, paths)` (§6); the guess uses `Commit` and `Tag`. The deployment search and its caches are untouched.

## 5. Configuration (`releases.yaml`)

- **Removed:** nothing for the user to remove. `refresh` keeps its meaning for "not a recent release" re-checks; it no longer refers to a git copy.
- **`compare_ref`:** `origin/HEAD` (default) is the project's default branch, `origin/<branch>` is `<branch>`. Any other form is a load error with its position (today any git reference was accepted).
- **`remote`:** unchanged: the remote of the clone, read from `.git/config`.
- `huginn.yaml` `repos_root`: still needed (the clones give the projects), unless §9's template is chosen.
- `docs/CONFIG.md` §11: the git paragraphs (Huginn's copy, `(local, may be stale)`, SSH batch mode) are replaced by the API calls and their cost. Users may delete `~/.cache/huginn/git`; Huginn no longer writes it.

## 6. Cost and caching

Per service the cursor rests on, the deployment search is unchanged (1 list + 1 log for the latest release, once per session). The commit details add:

| Case | Requests |
|---|---|
| First lookup of a service | default branch (1, then hourly per project) + trunk tip (1) + count (1) + on-trunk (1) = **3–4** |
| The same service a minute later (the TUI asks again while it stays selected), trunk unchanged | trunk tip (1); the count is reused |
| The trunk moved | tip (1) + count (1) + on-trunk (1) |
| Monorepo workload with *p* paths | + *p* when the tip moved |
| A guess from an image tag or a git tag | + 1 or 2, cached for the session (immutable) |

So about **one small request a minute** per selected service, and nothing for the others. GitLab's rate limits are far above that: 2 000 authenticated requests a minute on GitLab.com; self-managed instances set their own. Caches are in memory and bounded like M16's (4 096 entries): commits and tags for the session, counts by trunk tip, the default branch for an hour.

Gone: every git process (2 per lookup and per refresh in M16), the copy on disk, the first fetch of a large repository (M16's A-3).

## 7. Failure and security

| Case | Line |
|---|---|
| GitLab unreachable (VPN off) | `GitLab unreachable`; a release already found keeps its commit and subject for the session; no count |
| A count beyond `X-Total` | `10000+ not deployed on <branch>` |
| A path list over 100 commits | `100+ not deployed on <branch>` |
| Revision ranges refused by an old GitLab (to verify) | The `compare` fallback of §3, `N+` when capped |
| Token without repository read | `the token cannot read <project> (read_api scope and Reporter role needed)`, as today |
| The clone has no such remote, or `.git/config` is unreadable | `no clone of this repository in <repos_root>: …`, as today |

**The `.env` check without git:** the "readable by others" check is unchanged. The "not git-ignored" check runs when the config folder has a `.git` entry. It then reads the folder's `.gitignore` for a line that ignores the file (`.env`, `/.env`, `*.env`, `.env*`). It is simpler than git's full rules, so it may warn about a file that a parent `.gitignore` or a global excludes file already ignores; the message says how to silence it (add the line). It never misses a file that isn't ignored.

Security is unchanged: the same token, never logged, `GET` only, no redirect to another host. Ids, branches, tags and paths are validated and URL-encoded. **No process is started at all** by the feature.

## 8. Tests

- **GitLab `Commits` adapter**: an `httptest` GitLab for every request of §3 (default branch, tip, count from `X-Total`, `X-Total` missing, merge base, paths and the union of ids, abbreviated commit, tag and `v` tag, the `compare` fallback); errors per kind; the token never in an error. A shared `RunCommitLogContract` suite, run against it and the fake.
- **`GitRemote`**: `.git/config` with several remotes, quoting, `insteadOf`, a worktree and a submodule `.git` file, a missing remote, a folder that is not a clone.
- **App**: counts cached by tip (no count request when the tip did not move); `compare_ref` mapping; guesses through the API; the deployment search tests unchanged.
- **`.env` check**: each ignoring line, none, no `.git`.
- **Removed**: the `gitcli` tests, the git-process counting test, the stale-fallback tests.
- **QA** ([`M16-qa.md`](M16-qa.md) updated): A-2 (git without a prompt) and A-3 (first fetch) are dropped; added are the three API "to verify" points, requests per minute while resting on a service, and the counts compared with a fresh `git rev-list` run by hand as the oracle.

## 9. Decisions

**Decided by the owner (2026-11-21):** GitLab's API only; no `git` mode; git removed from the feature; consequently, offline means no count (the clone fallback was git's).

**Open:**
1. **Project of a repository:** read from the clone's `.git/config` only (recommended: nothing to configure, as today), or also allow a `project: "<group>/{repo}"` template in `releases.yaml` so that no clone is needed at all?
2. **Numbering:** M16.1, decision D-075 (M17, which had reserved it, is not planned).
