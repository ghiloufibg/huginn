# M16.1 — Commit details from GitLab's API instead of git  (status: design, awaiting owner decisions §9)

**Question (owner, 2026-11-21):** can Huginn read the commit message and the "not deployed" count **from the remote directly**, without fetching, in case the local clone is stale; otherwise, use the GitLab API it already calls, and not rely on git commands at all?

This is a design only. Nothing below is implemented. GitLab API facts that could not be checked here are marked **to verify** and join the QA of [`M16-qa.md`](M16-qa.md).

## 1. Answer: git cannot read a remote without fetching; the GitLab API can

| Way | What it can give | Verdict |
|---|---|---|
| `git ls-remote <url>` | Branch and tag names with their commit ids. **No message, no author, no count**: the git protocol only sends refs and objects | Not enough |
| `git archive --remote` | Files of a tree, not history; GitLab does not serve it over HTTPS, and not over SSH by default | Not usable |
| `git fetch` (what M16 does today) | Everything, after downloading commits | Works, but it is a download, and it needs git, SSH or HTTPS credentials, and disk |
| **GitLab REST API** (same token, `read_api`) | Message, author, dates, tag → commit, counts between two commits, per path | **Recommended**: no git, no download into a copy, always current |

**A clarification about today's code.** M16 does **not** read the possibly stale local clone, except as a fallback. It keeps **its own copy** of the remote (commits only, in `~/.cache/huginn/git`), fetched at most every minute, and never touches the clone. So the counts are already current. The local clone is read only when GitLab cannot be reached, and the line then says `(local, may be stale)`. What this design removes is git itself: the processes, the copy on disk, and the SSH or HTTPS credentials git needs.

## 2. What changes

| | Today (M16, `commits: git`) | This design (`commits: gitlab`) |
|---|---|---|
| Commit message | From GitLab's deployment; git only for guesses | Same; GitLab's commit API for guesses |
| "N not deployed", on the trunk or not | git `rev-list` on Huginn's copy | GitLab API (§3) |
| Git tag fallback | git `rev-parse` | GitLab tags API |
| Finding the GitLab project of a repository | `git remote get-url` on the clone | The clone's `.git/config` **read as a file** (no git process), or a template in the config, so no clone is needed at all (§5) |
| Needs git installed, SSH key or credential helper, disk | Yes | **No**: only the token Huginn already has |
| Offline (VPN off) | Falls back to the clone, `(local, may be stale)` | No count: `GitLab unreachable` (or a hybrid fallback, §9.3) |

Nothing else changes: the GitLab deployment search (the owner's algorithm), the COMMIT line, its states and the TUI stay as they are.

## 3. GitLab calls

All `GET`, REST v4, same client, token and error classification as the deployment search (`adapters/driven/gitlab`).

| Need | Request | Reads |
|---|---|---|
| The trunk's name (`origin/HEAD`) | `GET /projects/:id` | `default_branch`. Cached for an hour |
| The trunk's tip | `GET /projects/:id/repository/branches/:branch` | `commit.id`. Used as the cache key of the counts (§6) |
| **Not deployed** (commits on the trunk the running commit lacks) | `GET /projects/:id/repository/commits?ref_name=<sha>..<branch>&per_page=1` | the `X-Total` header = the count; **to verify**: that `ref_name` accepts a revision range on the owner's GitLab version, and that `X-Total` is sent |
| **On the trunk** | `GET /projects/:id/repository/merge_base?refs[]=<sha>&refs[]=<branch>` | the running commit is on the trunk when the merge base **is** it |
| Not deployed, **monorepo with `paths`** | the same commits request with `&path=<path>` per path, listing ids (`per_page=100`) and counting the union | exact up to 100 per path, then shown as `100+` (§6) |
| A commit's message (guesses, or a deployment without one) | `GET /projects/:id/repository/commits/:sha` | `id`, `title`, `author_name`, `committed_date`; **to verify**: that an abbreviated id from an image tag is accepted |
| Git tag fallback | `GET /projects/:id/repository/tags/:tag` | `commit.id` |

`X-Total` is not sent when a list is very large (GitLab drops it for performance, **to verify** the limit). The line then says `10000+ not deployed`, never a wrong number.

## 4. Ports and adapters

The `ports.CommitLog` port already has the right methods (`Commit`, `Tag`, `Count`, `Refresh`), so the change is a **second implementation**, selected by name:

```go
// adapters/driven/gitlab: Commits implements ports.CommitLog with the REST
// API. Refresh does nothing; stale is always false.
type Commits struct{ Client *Client }
```

One adjustment to the port, because the API needs the **project** where git needs a **folder**:

```go
type GitRepo struct {
    Dir, Remote string           // for the git implementation
    Project     ReleaseProject   // for the API implementation (filled by the app)
}
```

`RemoteURL`, git's way of finding the project, moves out of `CommitLog` into a small **project locator** used by the app for both implementations:

| Locator | How |
|---|---|
| `clone` (default) | Reads `repos_root/<repo>/.git/config` as a file (a worktree's `.git` file is followed) and takes `[remote "<remote>"] url`. No git process |
| `template` | `releases.yaml` `project: "payments/{repo}"`: no clone needed at all |

The app (`core/app/releases.go`) changes only where it calls `RemoteURL` and `Refresh`: with the API, `Refresh` is a no-op and the counts are cached by trunk tip (§6). The `gitcli` adapter stays for `commits: git`.

## 5. Configuration (`releases.yaml`)

```yaml
commits: gitlab            # gitlab (this design) | git (today's behavior)
# project: "payments/{repo}"   # optional: the GitLab project of a repository, when no clone is used
```

- `commits` defaults to `git` so that **nothing changes for an existing folder** (§9.1); the example and the docs show `gitlab`.
- `compare_ref` keeps its meaning: `origin/HEAD` is the project's default branch, `origin/<branch>` is `<branch>`. Any other value is a load error with `commits: gitlab`.
- `refresh` keeps its meaning for "not a recent release" re-checks; it no longer refers to a git copy.

## 6. Cost and caching

Per service the cursor rests on, the deployment search is unchanged (1 list + 1 log for the latest release, once per session). The commit details add:

| Case | Requests |
|---|---|
| First lookup of a service | default branch (1, then hourly) + trunk tip (1) + count (1) + on-trunk (1) = **3–4** |
| The same service a minute later, trunk unchanged | trunk tip (1); the count is reused because the tip did not move |
| The trunk moved | trunk tip (1) + count (1) + on-trunk (1) |
| Monorepo workload with *p* paths | + *p* list requests (at most 100 ids each) when the tip moved |
| Guess from an image tag or a git tag | + 1 or 2 (commit, tag), cached for the session (immutable) |

Compared with git: no process, no disk, no download. In exchange, about one request a minute per selected service, sent only while it stays selected. GitLab's rate limits (on GitLab.com, 2 000 authenticated requests a minute; self-managed instances set their own) are far above that. Counts are cached by `(project, sha, branch tip, paths)`; commits and tags for the session; every map is bounded like M16's (4 096 entries).

## 7. Failure and security

| Case | Line |
|---|---|
| GitLab unreachable (VPN off) | `GitLab unreachable`; a deployment already found keeps its commit and subject for the session; no count (§9.3 for a fallback) |
| A count too large for `X-Total` | `10000+ not deployed on <branch>` |
| A path list over 100 commits | `100+ not deployed on <branch>` |
| Revision ranges refused by an old GitLab (to verify) | Fall back to `compare?from=<sha>&to=<branch>` and count its `commits`. That answer also carries diffs, so it is heavier and capped by GitLab: shown as `N+` when capped |
| Token without repository read (a role below Reporter on a private project) | `the token cannot read <project> (read_api scope and Reporter role needed)`, as today |

Security is unchanged: the same token, never logged, `GET` only, no redirect to another host. Ids, branches and paths are URL-encoded and validated as today (hex ids, plain branch names). With `commits: gitlab`, Huginn runs **no git process at all**.

## 8. Tests

- **GitLab `Commits` adapter**: an `httptest` GitLab for every request of §3 (the default branch, the tip, the count from `X-Total`, `X-Total` missing, the merge base, paths and the union of ids, the commit, the tag, the `compare` fallback); errors per kind; the token never in an error.
- **Project locator**: `.git/config` with several remotes, a worktree, a missing remote, a `template`.
- **App**: counts cached by trunk tip (no count request when the tip did not move); `Refresh` not called with the API; `commits: git` unchanged (the existing tests pass untouched).
- **QA** (added to [`M16-qa.md`](M16-qa.md)): the same cases as M16, with `commits: gitlab`; the counts compared with a fresh `git rev-list` (the oracle); the three "to verify" API points; requests per minute while resting on a service; VPN off.

## 9. Decisions needed from the owner

1. **Default:** keep `commits: git` as the default so nothing changes until you switch (recommended), or make `gitlab` the default?
2. **Project of a repository:** read from the clone's `.git/config` as a file (recommended: nothing to configure), or a `project:` template so no clone is needed at all, or both?
3. **Offline:** with the API, should the count fall back to the local clone (with git, marked stale) when GitLab is unreachable, or show no count (recommended, since you asked not to rely on git)?
4. **Remove git entirely** later, if the API mode proves itself in the QA (`gitcli` and its copy deleted, one way only)? Or keep both?
5. **Numbering:** M16.1, decision D-075 (M17, which had reserved D-075, is not planned).
